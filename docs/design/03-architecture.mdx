## システム構成図

サーバー処理・データベースを持たない静的 PWA とする(T-001)。配信後はすべての処理を端末内で行う。

## コンポーネント設計

| コンポーネント | 責務 | 対応要件 |

| 画面(app/) | SCR-001〜SCR-010 の描画。static export で HTML 化 | FR-001〜FR-022 |
| 出題エンジン | 出題セット生成・正誤判定・タイマー・習得状況/復習/メダル更新の計算。UI に依存しない純粋な TypeScript モジュール | FR-002, FR-006, FR-007, FR-011〜FR-014 |

| サウンドプレイヤー | Web Audio API の初期化(タップでアンロック)、効果音・読み上げ音声の再生 | FR-008〜FR-010 |
| オフライン管理 | Service Worker 登録、音声の学年別ダウンロード、更新検知、インストール案内の判定 | FR-019, FR-020 |

### ディレクトリ構成

アプリ本体はリポジトリ直下のドキュメントサイト(Blume)と分け、独立した Next.js プロジェクトとして `web/` 配下に置く。Vercel の Root Directory も `web` とする。

| パス(`web/` 配下) | 内容 |
| --- | --- |
| `app/` | 画面(App Router。SCR-001〜SCR-010) |
| `src/engine/` | 出題エンジン(UI 非依存) |
| `src/store/` | 学習データストア(Dexie) |
| `src/data/` | 問題データの型・原稿変換・検証・ローダー |
| `src/audio/` | サウンドプレイヤー |
| `src/sw/` | Service Worker(Serwist)・端末判定 |
| `src/config.ts` | 設定定数(仮置きの設計パラメータ) |
| `content/` | 問題データ原稿(YAML)・配当表・公開済み問題 ID のロック |
| `public/data/` | 生成された問題データ JSON(ビルド時に生成。コミットしない) |
| `public/audio/` | 生成された音声ファイル(FR-009 実装時) |
| `public/fonts/` | サブセット化した Klee One(T-007 実装時) |
| `scripts/` | データ生成・検証・Service Worker 生成・アイコン生成(音声生成・フォントサブセット化は後続) |
| `e2e/` | E2E テスト(Playwright) |

## 配信データの構成とキャッシュ戦略

| 資産 | 想定サイズ | キャッシュ方式 | 取得タイミング |
| --- | --- | --- | --- |
| アプリ本体(HTML/JS/CSS) | 約 1MB | precache | 初回アクセス時 |
| フォント(Klee One サブセット) | 約 0.5〜1MB | precache | 初回アクセス時 |
| 効果音 | 約 50KB | precache | 初回アクセス時 |
| 問題データ manifest + 学年別 JSON(6 ファイル) | 合計 約 1.5MB(gzip 後 約 0.3〜0.5MB) | precache | 初回アクセス時 |
| 読み上げ音声 | 学年あたり 約 3〜6MB、合計 約 20〜30MB | ランタイムキャッシュ(Cache Storage) | 選択中の学年を優先して取得し、その後、残りの学年をバックグラウンドで順次取得 |

- 初回表示(NFR-002)に必要なのはアプリ本体・フォント・問題データのみとし、音声の取得を待たずに学習を開始できる
- 音声の取得が完了していない学年でも学習は可能(読み上げのみスキップ)

## セキュリティ設計

実現方式の詳細は [非機能設計](/design/nfr-spec) を参照。ここではインフラ・アーキテクチャ観点の要点のみ記載する。

- 全通信を HTTPS(Vercel 標準の TLS 1.2 以上)で配信し、HSTS を有効化する(NFR-009)
- `vercel.json` でセキュリティヘッダー(CSP・X-Content-Type-Options・Referrer-Policy・Permissions-Policy)を付与する
- 外部ドメインへの通信は行わない(CSP の `connect-src 'self'`)。学習データは端末外に出ない(NFR-010)
- 認証機能を持たないため、認証・権限管理は対象外
- ステージングは Vercel Authentication で保護する

## 運用設計

実現方式の詳細は [非機能設計](/design/nfr-spec) を参照。ここではインフラ・アーキテクチャ観点の要点のみ記載する。

| 項目 | 方針 | 対応要件 |
| --- | --- | --- |
| バックアップ | サーバー側に可変データはない。ソース・問題データ・音声は GitHub で管理。端末内の学習データはバックアップしない | NFR-014 |
| デプロイ | GitHub への push で Vercel が自動ビルド・デプロイ。ビルド時に問題データ検証を実行し、失敗時はデプロイしない | NFR-012, NFR-013 |
| ロールバック | Vercel の Instant Rollback で直前のデプロイへ戻す | NFR-003 |
| 監視 | Vercel のデプロイ失敗通知(メール)。外部監視サービスは使わない(静的配信のため) | NFR-003 |
| 問い合わせ・障害対応 | 保守契約なし。発生時にスポット対応として見積もる {/* TODO: 利用者からの問題データ誤り報告の受付窓口(顧客側で用意するか)を確認 */} | NFR-012 |
| 依存ライブラリ更新 | 保守契約なし。セキュリティ更新はスポット対応(年 1〜2 回を推奨) | NFR-009 |
